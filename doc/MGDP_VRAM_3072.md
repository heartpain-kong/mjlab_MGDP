# 保留20列的显存优化与3072环境试运行

用户实测2048环境、8行启动时显存约7.5/8GB。本次保留20列、以8行为试运行配置，
不减少单块障碍密度，不关闭HIMLoco域随机化，不改变奖励和力矩上限。
本机只有CPU验证环境，没有在用户RTX4060 Laptop上实测3072容量，不能保证8GB可稳定长训。

后续用户8×20/2048已明确在BVH常驻数组分配时CUDA OOM。
当前结构下3072仅配对查找表、几何体姿态和BVH叶子三项就约8.94GiB；
3072预设只能供更大显存设备筛查，不能作为8GB卡可行性承诺。
最新诊断命令使用512环境并保留8×20地图，见[CUDA初始化诊断](MGDP_CUDA_DIAGNOSTICS.md)。

## 不改变模型权重的优化

### 分块构建碰撞对，跳过闲置完整表

本地MuJoCo Warp 3.5.0创建 `nxn_geom_pair` 与过滤后的 `nxn_geom_pair_filtered`。
实际NXN碰撞路径传入后者；SAP使用另一张 `nxn_pairid` 查找表。
此前在模型上传返回后释放完整表，仍会先经历原生构造峰值。用户的8×20、2048环境在该阶段以−9退出，
因此现在在分配前替换经过精确源码校验的配对构建代码块：每批最多262144对，直接写入int32查找表，
不生成全量int64几何体索引、堆叠数组和过滤临时数组，也不上传闲置完整 `nxn_geom_pair`。
**保留**过滤后的几何体对、完整pair-id查找、碰撞算法、接触/约束容量和求解器迭代数。

完整表包含 `ngeom*(ngeom-1)/2` 个int32二元组，即约 `4*ngeom*(ngeom-1)` 字节。
场景27838个几何体时，仅这一闲置设备表就是约2.89GiB。启动应出现：

```text
[memory] bounded host pair construction enabled (verified mujoco-warp 3.5.0)
[memory] streaming collision pairs: geoms=27838, pairs=387463203, chunk=262144; retained dense lookup=2.89 GiB; skipping unused full geom-pair table
```

实现位于 `src/sim_memory.py`。目前仅对已验证的mujoco-warp 3.5.0尝试启用，
启动时还检查已安装内核源码和待替换代码块指纹：若其他运行函数读取完整表，或源码/版本无法验证，
则保留原分配并打印说明。源码指纹兼容Python3.11/3.12空type_params字段差异。
工厂适配只包围环境构造，结束或抛出异常时恢复，不修改安装目录中的文件。
保留的完整pair-id查找表仍随几何体数量平方增长，27838个几何体时约2.89GiB，
上传时还可能产生主机拷贝；这不是整个进程RAM或GPU显存总量。
优化避免了原生11.55GiB索引估算对应的分配及其他全量过滤临时量，并未消除所有平方开销。
详细故障说明与验证见[碰撞建表内存修复](MGDP_HOST_PAIR_MEMORY.md)。

### 冻结感知分批推理并清理重建缓存

策略采样时默认按256个环境一批执行深度编码器与GRU，每个环境的隐藏状态独立切分、原序拼回。
使用的GroupNorm/LayerNorm不跨样本归一化，权重、特征维度、两帧输入和GRU复位规则保持一致。
提取特征后清空仅重建解码器需要的skip缓存；预训练损失依然重新创建skip特征并正常反向传播。
这些调整不改变感知模型参数指纹，已有配套策略/感知文件仍可使用。

`inference_batch_size` 位于感知观测项参数中，默认256；设0选择整批推理。
原生训练/Play脚本的 `--optimize-vram False` 关闭后端分块建表、跳过闲置表及下述BVH优化；
`lgdog.py`短命令和预训练脚本对应 `--no-optimize-vram`。
感知分批大小独立控制，便于分别比较内存和速度。

### 深度传感器 BVH 初始化共享暂存

用户6×20、2048环境运行在主机建表成功后，明确出现CUDA OOM：
BVH初始化为所有环境复制旋转矩阵，单次申请1540177920字节失败。
现在只计算一次相同初始包围盒，再写入各环境独立BVH，避免约2.39GiB重复尺寸/姿态暂存。
物理域随机化字段扩展还会复用原Context，避免不必要的第二份BVH；视觉字段仍按原生规则重建。
这些后端优化由同一optimize-vram开关控制，详细证据、版本校验和限制见
[深度传感器显存修复](MGDP_SENSOR_VRAM.md)。这不是整轮训练显存的实测下降量。

## 入口预设

| 预设 | 环境数 | 行×列 | 轮数 | PPO小批次数 |
|---|---:|---|---:|---:|
| 快速检查 | 64 | 2×20 | 2 | 4 |
| 正式训练 | 2048 | 8×20 | 16000 | 4 |
| 3072环境试运行 | 3072 | 8×20 | 2 | 8 |

8个小批次减小每次反向传播的样本数，但会改变优化批量与更新次数，不能当成与4小批次相同的训练实验。
50步rollout下，3072×50/8=19200个样本/小批次，小于原2048×50/4=25600。
rollout总存储仍随环境数增长；增加小批次数不会减少物理显存或全部rollout存储。

工作台保留原有按钮和参数排版，3072试运行通过命令行启动。在已激活训练环境、项目根目录运行：

```bash
python -u lgdog.py train race_mgdp --envs 3072 --iterations 2 \
  --terrain-num-rows 8 --terrain-num-cols 20 --ppo-mini-batches 8
```

日志在物理环境初始化、runner初始化以及PPO结束阶段输出显存快照。
`device/global` 包含其他进程；`Torch peak reserved` 仅是PyTorch分配器峰值，不包含Warp，不能当成整个任务峰值。
应确认完整采样、PPO更新和检查点保存，观察RAM和nvidia-smi，而非只看启动成功。
3072成功也只是容量筛查，稳定性、吞吐与越障表现需要后续训练验证；GPU OOM后可退回已能运行的2048配置。
改变环境数或地图网格时须新建run，不能直接恢复不同规模的课程统计。

## 本地验证

临时记录位于忽略目录 `.artifacts/vram-3072/`：

- 10环境、2×10地图的实际CPU模型有3516个几何体，避免闲置设备表49,434,960字节（约47.1MiB）。
- `nxn_pairid`、过滤后的几何体对及全部物理Data容量不变；Data总量仍为3,683,288字节。
- NXN及SAP_SEGMENTED两种路径，原版/优化后各运行12个控制步，轨迹、奖励、本体观测在容差内一致。
- 感知整批/分批推理跨时间及部分环境复位结果一致；参数指纹不变，预训练反向传播通过。
- CPU PPO更新、保存、ONNX导出、恢复后再次更新通过。
- 8个PPO小批次的CPU更新、保存、恢复也通过；原版显存优化全套290项测试0失败、1跳过，
  本次分块修复的新增验证见上述碰撞建表内存说明。

以上不是8GB GPU的3072长训实测。特别是较大场景仍保留完整pair-id表及每环境几何体姿态、
摩擦等数据，它们构成无法靠本次清缓存完全消除的显存开销。
