# 比赛策略训练：主机内存 OOM 排查与小地图预设

日期：2026-11-05。

## 这次失败的证据

用户提供的 Linux 内核日志明确记录：22:17:07 出现 `global_oom`，被杀的是
训练进程 `python` / PID 5482，退出码 −9（SIGKILL）。其 `anon-rss` 为 `29519480kB`
（约28.2GiB），系统约31GiB RAM、没有swap。日志显示地形生成耗时112.672秒后退出，未进入PPO更新。
这是一次已确认的**主机RAM耗尽**。GPU是否也会不足，需要在对应配置下独立测量。

原参数：2048环境、12行×20列比赛课程。前一次提交只减小了感知预训练地图，
没有把策略训练的工作台参数改成小内存预设，因此这次策略训练仍使用大图。

## 为什么只减环境数不够

本地安装的 `mujoco_warp._src.io.put_model` 先执行 `np.triu_indices(ngeom, k=1)`，
再堆叠成几何体对表，之后才按碰撞掩码和静态身体关系过滤。
索引数量为 `ngeom*(ngeom-1)/2`，随全图几何体数平方增长；这个建表阶段不依赖环境数。

在当前实现中，两条int64索引向量和堆叠数组同时存在时，仅这部分就约需 `32×pair_count` 字节主机内存。
后续身体ID、碰撞掩码、接触对等数组还会增加内存；不能把此估算当成总峰值。
每个环境的几何体位置和旋转还至少需要 `48×ngeom` 字节设备存储，同样不包含全部GPU分配。
后端更新后算法和估算适用性可能变化；当前运行会打印实际场景几何体数和这两项估算。

逐课程生成单块原生几何体，按均匀列比例展开，得到以下近似值。未计入机器人和边界，
不构成完整场景实测内存，也不保证某种GPU一定能容纳。

| 行×列 / 环境数 | 赛道几何体约数 | 仅上述索引数组的RAM估算 | 仅几何体姿态的设备存储 |
|---|---:|---:|---:|
| 12×20 / 2048 | 41,688～41,736 | 25.90～25.96GiB | 3.82GiB |
| 4×10 / 256 | 6,948～6,956 | 0.72GiB | 0.080GiB |
| 2×10 / 64 | 3,474～3,478 | 0.18GiB | 0.010GiB |

这些估算与用户提供的RAM OOM时点相符。单独降低环境数不能降低上述主机建表开销，
因此需要同时减小重复地形块数量。

## 已修改的行为

- 工作台及 `lgdog.py train race_mgdp` 默认：**256环境、4×10地图、16000轮**。
- 快速检查：**64环境、2×10地图、2轮**。
- 新增“地形训练列数”，并从工作台、短命令传递至原生 `--terrain-num-cols`。
  比赛至少10列，保留全部10类障碍；完整地图定义仍为10×20，显式填写的大配置不会被悄悄截断。
- 切换到比赛任务时填入默认预设；普通刷新不覆盖手工修改。失败记录显示已有退出码。
- 初始化先打印网格规模，场景组装后打印实际几何体数、索引内存估算，再进入模型编译和物理缓冲分配。
  原有场景回调会被保留，临时诊断回调在初始化后恢复，不写入检查点配置。
- 单块的密集高墙、匍匐、轮胎等尺寸与数量、奖励、感知维度和HIMLoco全强度扰动不变。
  行数变少意味着课程档位变少，仍覆盖0～1难度范围，需要新建run重新积累晋级统计。

## Linux 使用

更新代码并重启工作台服务、刷新页面后，重新选择 `race_mgdp` 并点击“快速检查”。
查看命令应包含64环境、2行、10列；通过后再切“正式训练”。也可在项目根目录运行：

```bash
# 在已激活的训练环境中；先验证链路
python -u lgdog.py train race_mgdp --envs 64 --iterations 2 \
  --terrain-num-rows 2 --terrain-num-cols 10

# 确认本机资源允许后，再开始新run
python -u lgdog.py train race_mgdp --envs 256 --iterations 16000 \
  --terrain-num-rows 4 --terrain-num-cols 10
```

大地图Play等其他进程也可能占用主机内存及显存，排查时应一并查看资源占用。
`MemoryMax` 约束整个服务cgroup及其子进程，不能保证只终止训练；它不是训练进程隔离方案，
也不能替代减少本次几何体建表开销。
